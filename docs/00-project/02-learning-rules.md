# Python Learning Rules

## 1. Mục đích

Tài liệu này quy định cách học Python trong repository `python`.

Mục tiêu không chỉ là hoàn thành bài tập mà là xây dựng khả năng:

- hiểu bản chất của Python;
- tự viết code;
- đọc và phân tích code;
- kiểm tra và sửa lỗi;
- giải thích được code mình viết;
- sử dụng Git để lưu lại quá trình học;
- áp dụng kiến thức vào các bài toán và project thực tế.

---

## 2. Nguyên tắc học tập

### Rule 01 — Hiểu trước khi code

Trước khi viết code phải hiểu:

- bài toán yêu cầu gì;
- dữ liệu đầu vào là gì;
- kết quả đầu ra là gì;
- kiến thức Python nào được sử dụng;
- cách giải quyết dự kiến.

Không chạy theo việc viết code thật nhanh.

---

### Rule 02 — Tự giải quyết trước khi xem lời giải

Khi gặp bài tập:

1. Đọc và phân tích yêu cầu.
2. Tự suy nghĩ cách giải.
3. Tự viết code.
4. Tự chạy thử.
5. Tự sửa lỗi.
6. Chỉ xem gợi ý hoặc lời giải khi thực sự cần.

Mục tiêu là hình thành khả năng giải quyết vấn đề, không phải ghi nhớ lời giải.

---

### Rule 03 — AI là Mentor, không phải người làm thay

AI được sử dụng để:

- giải thích khái niệm;
- phân tích lỗi;
- đặt câu hỏi gợi mở;
- review code;
- chỉ ra điểm chưa hiểu;
- đề xuất bài tập bổ sung;
- giải thích cách tiếp cận khác nhau.

Không sử dụng AI để hoàn thành toàn bộ bài tập khi chưa tự suy nghĩ.

Nếu AI cung cấp code mẫu, người học phải:

1. đọc code;
2. hiểu từng phần;
3. tự giải thích được;
4. tự chạy thử;
5. có khả năng viết lại hoặc biến đổi code.

---

### Rule 04 — Một TASK có một mục tiêu chính

Mỗi TASK phải có một mục tiêu học tập chính.

Ví dụ:

```text
TASK — Variables
Mục tiêu:
Hiểu cách khai báo và sử dụng biến trong Python.
```

Không đưa quá nhiều kiến thức mới vào một TASK nếu chúng không cần thiết cho mục tiêu chính.

---

### Rule 05 — Học từ đơn giản đến phức tạp

Thứ tự ưu tiên:

```text
Khái niệm
    ↓
Ví dụ đơn giản
    ↓
Bài tập nhỏ
    ↓
Bài tập tổng hợp
    ↓
TASK
    ↓
Mini Project
    ↓
Project
```

Không nhảy quá nhanh sang kiến thức nâng cao khi nền tảng chưa vững.

---

## 3. Quy trình thực hiện TASK

Mỗi TASK thực hiện theo quy trình:

```text
Requirement
    ↓
Understand
    ↓
Plan
    ↓
Implement
    ↓
Self-Test
    ↓
Review
    ↓
Documentation
    ↓
Git
    ↓
Progress Update
    ↓
PASS
```

### Requirement

Xác định rõ:

- mục tiêu;
- phạm vi;
- kiến thức cần học;
- Acceptance Criteria.

### Understand

Người học phải hiểu nội dung trước khi bắt đầu code.

### Plan

Xác định cách tiếp cận và các bước giải quyết.

### Implement

Viết code theo phạm vi của TASK.

### Self-Test

Tự kiểm tra bằng các trường hợp phù hợp.

### Review

Kiểm tra:

- code có đúng không;
- code có dễ đọc không;
- có lỗi logic không;
- có phần nào chưa hiểu không;
- có phần nào thừa hoặc phức tạp không.

### Documentation

Cập nhật tài liệu liên quan nếu TASK yêu cầu.

### Git

Kiểm tra thay đổi trước khi commit.

### Progress Update

Cập nhật tiến độ học tập.

### PASS

Chỉ chuyển TASK sang `PASS` khi Acceptance Criteria đã hoàn thành.

---

## 4. Không PASS khi chưa hiểu

Một TASK không được đánh dấu `PASS` chỉ vì:

- code chạy được;
- chương trình không báo lỗi;
- AI xác nhận code đúng;
- copy được lời giải;
- hoàn thành nhanh.

TASK chỉ được PASS khi người học có thể:

- giải thích được kiến thức chính;
- giải thích được code;
- tự chạy và kiểm tra;
- nhận biết lỗi cơ bản;
- sửa được lỗi phù hợp với trình độ;
- hoàn thành Acceptance Criteria.

---

## 5. Khi gặp lỗi

Lỗi là một phần của quá trình học.

Quy trình xử lý:

```text
Lỗi
 ↓
Đọc thông báo lỗi
 ↓
Xác định vị trí
 ↓
Phân tích nguyên nhân
 ↓
Tự sửa
 ↓
Chạy lại
 ↓
Kiểm tra kết quả
```

Không sửa lỗi bằng cách thay đổi code ngẫu nhiên cho đến khi chương trình chạy.

Cần cố gắng hiểu:

- lỗi xảy ra ở đâu;
- tại sao lỗi xảy ra;
- cách sửa;
- làm thế nào để tránh lỗi tương tự.

---

## 6. Quy tắc khi TASK FAIL

Nếu TASK chưa đạt yêu cầu:

```text
PASS
FAIL
BLOCKED
TODO
IN PROGRESS
```

được sử dụng để phản ánh đúng trạng thái.

Không xóa lịch sử FAIL để làm cho tiến độ đẹp hơn.

FAIL là dữ liệu học tập quan trọng.

Sau khi sửa và kiểm tra lại, TASK có thể chuyển sang `PASS`.

---

## 7. Quy tắc khi BLOCKED

TASK được đánh dấu `BLOCKED` khi không thể tiếp tục do một nguyên nhân bên ngoài hoặc thiếu điều kiện cần thiết.

Ví dụ:

- môi trường chưa cài đặt;
- thiếu dependency;
- thiếu dữ liệu;
- lỗi hệ thống;
- kiến thức prerequisite chưa hoàn thành.

Khi BLOCKED phải ghi rõ:

- nguyên nhân;
- điều kiện cần để tiếp tục;
- hướng xử lý dự kiến.

---

## 8. Quy tắc viết code

Ưu tiên:

- rõ ràng;
- dễ đọc;
- đơn giản;
- đúng bản chất;
- dễ kiểm tra;
- dễ sửa đổi.

Không ưu tiên:

- code quá ngắn nhưng khó hiểu;
- kỹ thuật nâng cao khi chưa cần;
- tối ưu hóa sớm;
- kiến trúc phức tạp;
- copy code mà không hiểu.

Nguyên tắc:

> Code dành cho con người đọc trước, máy tính thực thi sau.

---

## 9. Quy tắc đặt tên

Tên biến, hàm, class và file phải thể hiện được mục đích.

Ưu tiên:

```python
student_name
total_score
calculate_average()
```

Không ưu tiên:

```python
a
x1
abc
foo
```

trừ khi dùng trong ví dụ rất ngắn hoặc ngữ cảnh đặc biệt.

---

## 10. Quy tắc kiểm tra code

Mỗi TASK phải có kiểm tra phù hợp.

Tùy nội dung có thể sử dụng:

- chạy trực tiếp chương trình;
- test nhiều input;
- test trường hợp biên;
- kiểm tra output;
- kiểm tra lỗi;
- assertion;
- unit test ở các Level phù hợp.

Không chỉ kiểm tra một trường hợp duy nhất.

---

## 11. Quy tắc documentation

Documentation là một phần của quá trình học.

Tài liệu có thể ghi:

- kiến thức đã học;
- điều đã hiểu;
- điều chưa hiểu;
- lỗi gặp phải;
- cách xử lý;
- bài học rút ra;
- quyết định thiết kế;
- tiến độ TASK.

Không cần viết tài liệu dài nếu nội dung không cần thiết.

Ưu tiên:

> ngắn gọn nhưng đủ để người khác hiểu và bản thân có thể xem lại sau này.

---

## 12. Quy tắc Git

Git là một phần của quá trình học.

Trước khi commit phải kiểm tra:

```powershell
git status
git diff
git diff --check
```

Sau đó mới:

```powershell
git add .
git commit
git push
```

Commit message phải mô tả đúng thay đổi.

Ví dụ:

```text
feat(task-01): add variables exercises
docs(task-01): document variables lesson
fix(task-01): correct input validation
```

Không commit những thay đổi không liên quan đến TASK hiện tại.

---

## 13. Không chuyển TASK quá sớm

Không bắt đầu TASK mới chỉ vì TASK hiện tại đã có code chạy được.

Cần hoàn thành:

- mục tiêu;
- phạm vi;
- Acceptance Criteria;
- self-test;
- review;
- documentation nếu có;
- Git;
- progress update.

Sau đó mới chuyển TASK tiếp theo.

---

## 14. Khi kiến thức chưa vững

Nếu trong quá trình review phát hiện kiến thức chưa vững:

- dừng TASK nếu cần;
- bổ sung bài tập;
- tạo TASK phụ nếu cần;
- học lại phần kiến thức còn thiếu;
- kiểm tra lại.

Roadmap có thể được điều chỉnh theo nhu cầu thực tế.

Không cố hoàn thành roadmap bằng cách bỏ qua lỗ hổng kiến thức.

---

## 15. Nguyên tắc không chạy theo số lượng

Số lượng TASK không phải mục tiêu chính.

Quan trọng hơn là:

```text
Hiểu
 ↓
Tự làm
 ↓
Kiểm tra
 ↓
Sửa lỗi
 ↓
Giải thích
 ↓
Áp dụng
```

Một TASK được thiết kế tốt và hiểu sâu có giá trị hơn nhiều TASK chỉ hoàn thành hình thức.

## 16. Tiêu chuẩn hoàn thành một Level

Một Level chỉ được xem là hoàn thành khi người học có thể:

- giải thích các khái niệm chính;
- tự thực hiện các bài tập phù hợp;
- đọc và hiểu code cơ bản;
- tự tìm và sửa các lỗi phù hợp;
- hoàn thành các TASK cần thiết;
- hoàn thành Mini Project;
- giải thích được cách hoạt động của Mini Project;
- xác định được những điểm còn yếu;
- cập nhật documentation và progress.
